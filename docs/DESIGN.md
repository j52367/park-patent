# PARK — Patent Analysis Research Kit (가칭) 설계 문서 v0.2

> 한국 특허(KIPRIS)를 중심으로 **선행기술조사 → 기술 관련성 선별 → 특허맵 → 청구항 대비 → 전략·보고서**를
> 근거 인용과 함께 수행하는 Claude Code용 스킬팩. ARIS 방식(스킬 조합 + 다른 모델의 검토)을 특허 *분석* 쪽에 적용한다.

작성일: 2026-11-09 · 상태: v0.3 — 0단계 구현 중 (변경 내역은 §11)

---

## 1. 왜 만드나 — 포지셔닝

| 기존 오픈소스 | 하는 일 | 비어 있는 부분 |
|---|---|---|
| **ARIS** `patent-pipeline` (MIT) | **출원서 작성**(출원인 쪽): 선행조사 → 신규성 검토 → 청구항 → 명세서 → 심사관 리뷰 → CN/US/EP 서식 | 한국(KR) 미지원, 선행조사는 WebSearch 기반, **특허 분석(동향·유효특허·전략) 없음** |
| **claude-for-legal** `ip-legal` (Apache-2.0) | 미국 사내 IP 변호사 업무: FTO 선별, 발명 접수 1차 검토, 침해 선별, 포트폴리오 | 미국 법 중심, 유료 데이터 커넥터 전제, 동향/맵/전략 없음 |
| **KIPRIS MCP 서버들** (khreat, SilverQ, nuri428 등) | KIPRIS Plus API 검색 도구 | 검색에서 끝남. 분석 워크플로우 없음 |
| **PatentAgentBench** (MIT) | 신규성·무효·FTO 검색, 청구항 대비표, 명세서 작성 평가 (CN/US) | KR 데이터 없음 |

**PARK의 자리:** 한국 특허 + *분석* 업무. 캠퍼스 특허 유니버시아드(CPU), 특허청 IP-R&D·특허동향조사, 스타트업·연구실의 "이 기술 특허 상황이 어때?" 질문에 답하는 보고서를 만든다.
ARIS의 출원서 작성 기능과는 겹치지 않고 서로 보완한다. 나중에 ARIS에 KR 관할 지원을 기여하는 것도 가능하다.

PatentAgentBench 결과를 보면 LLM 에이전트는 그럴듯한 문서는 잘 쓰지만 **근거 검색과 근거에 기반한 추론**이 약하다.
그래서 PARK의 핵심 원칙은 "모든 판단에 원문 근거를 단다"이다.

**결론의 범위를 검색 범위에 맞춘다.** 한국 특허법상 신규성·진보성 판단의 선행기술은 국내외 공개 전부(해외 특허, 논문, 제품)다(특허법 제29조).
그래서 KR 특허만 검색한 결과는 **"KR 공개특허 동향"**이라고 부르고, 신규성이나 공백기술을 단정하지 않는다. 해외·비특허 문헌 검색이 붙은 뒤에야 그런 표현을 허용한다.

## 2. 사용자와 대표 시나리오

1. **CPU 참가 학생**: 기업이 낸 과제(예: "자율주행 라이다 신호처리")를 받아 기술 분류 → 검색식 → 유효특허 → 특허맵 → 핵심특허 대비 → 전략 제안 → 발표 자료까지.
2. **스타트업·연구실**: 우리 기술 설명을 주면 관련 특허 동향과 주의할 특허 목록을 받는다.
3. **실무 보조**: 변리사·연구원이 1차 스크리닝과 맵 작성을 맡긴다. 최종 판단은 사람이 한다.

## 3. 설계 원칙

1. **Markdown 스킬 + 얇은 Python 도구.** 판단은 LLM이 하고, 숫자·차트·API 호출은 결정적인 스크립트가 한다. 통계를 LLM이 지어내지 않게 하기 위해서다.
2. **근거 강제, 근거의 등급 구분.** 모든 판정에 `출원번호 + 문헌 종류(공개/등록/정정) + 위치(청구항·문단 번호 또는 '요약') + 원문 인용`을 단다.
   - 요약·서지만 보고 내린 판정은 **잠정(provisional)**으로 표시한다.
   - 청구항·명세서 전문을 보고 내린 판정만 **확정(confirmed)**으로 표시한다.
   - 근거가 없으면 "근거 없음"으로 표시하고 결론에 쓰지 않는다.
3. **기준일 관리.** 문헌마다 출원일, 우선일, 공개일, 등록일을 저장한다. 비교할 때는 대상 청구항의 기준일보다 앞서 공개된 문헌인지 확인한다.
4. **재현성.** 검색식, 검색 시각, 결과 수, 문헌 버전을 `SEARCH_LOG.md`에 남긴다. API 응답은 로컬에 캐시한다.
5. **공방형 검토(2단계).** 다른 모델의 검토 단계를 무효심판 구조로 바꾼다. 청구인과 피청구인이 다투고 심판관이 쟁점을 정리한다. 검토 백엔드는 교체할 수 있다(§4).
6. **체크포인트.** 기술 분류표, 검색식, 유효특허 목록을 확정할 때 사용자 확인을 받는다.
7. **API 쿼터 존중.** KIPRIS Plus 무료 한도는 문헌 수가 아니라 **호출 횟수** 기준(월 1,000회)이다. 그래서 한 페이지에 최대한 많이 받아 오고, 캐시하고, 남은 호출 수를 표시한다.
8. **기밀 보호.** 사용자 기술 설명 같은 기밀 입력을 외부 모델(Codex 등)로 보낼지는 사용자가 정하고, 기본값은 보내지 않음이다.
9. **법률 의견이 아님.** 모든 산출물에 면책 문구를 넣고, 무효·침해 "결론"이 아니라 "검토 의견 초안"으로 표기한다.

## 4. 아키텍처

```
사용자 ─ /park-pipeline (오케스트레이터 스킬)
            │
            ├─ skills/<이름>/SKILL.md    판단·서술 (LLM). Agent Skills 규격, 설치 가능한 패키지
            │     └─ 검토 백엔드         기본: Claude 서브에이전트 / 선택: Codex CLI 등
            │
            ├─ park/ (Python CLI)        결정적 작업
            │     ├─ kipris.py           KIPRIS Plus 클라이언트 + 캐시(SQLite) + 호출 수 관리
            │     ├─ ingest.py           CSV/엑셀 반입 (KIPRIS 웹 다운로드, 다른 DB 내보내기)
            │     ├─ normalize.py        중복 제거(공개·등록), 출원인 이름 정규화, 패밀리 묶기
            │     ├─ screen.py           BM25/임베딩 1차 정렬 (B 모듈 연결 지점)
            │     ├─ stats.py            집계 (§5.1 규칙)
            │     └─ charts.py           특허맵 차트 (SVG + HTML)
            │
            └─ analysis/<프로젝트>/       모든 중간 산출물 (버전이 붙은 스키마 = 스킬 간 인터페이스)
```

- **입력 경로가 둘이다:** (a) KIPRIS Plus API, (b) **CSV 반입**. API 키가 없어도 KIPRIS 웹에서 내려받은 엑셀이나 다른 DB에서 내보낸 파일로 바로 쓸 수 있게 한다. 채택 장벽을 낮추기 위해서다.
- **검토 백엔드:** Claude 서브에이전트가 기본이다. 작성자 환경에서는 WSL의 Codex CLI를 쓴다. 이것은 선택 사항이며 설치에 필요하지 않다.
- **산출물 스키마:** `candidates.csv`, `screening.csv` 등에 `schema_version`을 두고, 중간에 끊겨도 마지막 산출물부터 다시 시작할 수 있게 한다.

### 5.1 선별 라벨 — 세 축을 따로 둔다
한 칸에 "노이즈/유효/핵심"을 몰아넣지 않는다. 관련성과 중요도와 권리 상태는 서로 다른 질문이기 때문이다.

| 축 | 값 | 판단 주체 |
|---|---|---|
| 관련성 | 노이즈 / 유효(+기술분류 코드) | `/relevance-screening` (MVP) |
| 중요도 | 일반 / 주목 / 핵심 + 근거 | `/key-patent-review` (2단계) |
| 권리 상태 | 공개 / 등록(존속) / 소멸 / 거절 / 취하 / 포기 + 조회 시점 | API·데이터 (결정적) |

### 5.2 특허맵 집계 규칙 (`stats.py`)
- 공개문헌과 등록문헌은 **출원번호 기준으로 1건**으로 센다. 패밀리 단위 집계는 옵션으로 둔다.
- 출원인 이름을 정규화한다(예: "삼성전자주식회사"와 "삼성전자 주식회사"). 별칭 사전은 사용자가 고칠 수 있다.
- 공동출원은 기본적으로 출원인마다 1건씩 센다(full counting). 분할 집계(fractional)는 옵션이다.
- 국적은 출원인 주소 국가를 기준으로 하고, 정의를 보고서에 적는다.
- **미공개 구간 표시:** 출원 후 약 18개월 안에는 공개되지 않은 출원이 많다. 최근 구간은 음영으로 표시하고 "감소"로 해석하지 않는다.
- 기술 성장단계(출원인 수 × 출원 건수) 그래프는 참고 지표로만 표시하고, 성장단계를 단정하지 않는다.

### 5.3 청구항 대비 모드 (`/claim-chart-kr`, 2단계)
| 모드 | 비교 방식 | 근거 |
|---|---|---|
| 신규성 | 청구항 대 **단일** 선행문헌, 구성요소 전부 대응 여부 | 특허법 제29조 제1항 |
| 진보성 | 주 선행문헌 + 보조 문헌의 **결합 논리**, 결합 동기 | 제29조 제2항 |
| 침해·회피설계 | 제품 대 청구항, 청구범위 해석, 전 구성요소 대응, 균등 여부 | 제97조, 판례상 균등론 |

## 6. 데이터

### 6.1 KIPRIS Plus
- 호출 한도는 월 1,000**회**다. 한 번에 받을 수 있는 최대 건수(30–500건으로 알려짐)는 서비스마다 다르므로 실제 응답으로 확인한다.
- 서비스는 상품별로 신청해야 하고, 연간 갱신 조건이 있다.
- 0단계에서 **실제 응답으로 확인할 것**: 검색(`freeSearchInfo`), 서지, 청구항 전문 제공 여부, 행정 상태, 패밀리(`getFamilySearch`, 지난 학기에 실패 이력 있음), 인용 정보.

### 6.2 지난 학기 데이터 (`../옛날/`)
지난 학기 데이터 구성:
- `patents_raw.csv`: 9,976건. 전부 IPC G06N이 포함된 KR 출원(2014–2019)이며, 서지·요약·IPC·출원인·등록 상태가 있다. 청구항 본문과 인용 정보는 없다.
  → **이 데이터로 낸 판정은 모두 '잠정' 등급이다.**
- `patents_target.csv`의 `is_core_patent`: 확인해 보니 **등록 여부(`is_registered`)와 100% 같다.** 패밀리 API가 실패했을 때 쓰도록 한 대체 라벨이 들어간 것으로 보인다. PARK에서는 `is_registered`로만 다루고 중요도 라벨로 쓰지 않는다.
- `patents_family_target.csv`: 836건만 패밀리 라벨이 있다 (패밀리 있음 353 / 없음 483).
- 노트북의 KIPRIS 호출 코드는 `park/kipris.py`의 출발점으로 쓴다.

활용 계획:
1. **CSV 반입 경로 개발과 회귀 테스트 데이터** (로컬 전용).
2. **특허맵 데모:** 6년치 동향과 출원인 분석. 2019년 하반기 미공개 구간 처리를 검증하기에 알맞다.
3. **공개 저장소용 데모 데이터:** 원본은 커밋하지 않는다. 같은 스키마의 **합성 데이터**를 만들어 API 키 없이 돌아가는 데모와 CI에 쓴다.

## 7. B 모듈 — 한국어 특허 검색 모델 (3090 활용, 3단계)

- 목표: `/relevance-screening`의 1차 정렬을 로컬 모델로 수행해서 API 비용을 줄이고 기밀 자료도 처리할 수 있게 한다.
- 방법: PaECTER 방식. 심사관 인용 쌍으로 대조 학습(contrastive)을 해서 한국어 임베딩 모델 또는 cross-encoder 리랭커를 미세조정한다. 인용 데이터를 확보할 수 있는지가 전제 조건이다.
- 기준선: BM25 → 다국어 범용 임베딩 → (영어 경로) PaECTER.
- 결과물: Hugging Face 모델 공개 + 평가 보고서.

## 8. 평가 — 놓친 것을 잡는 지표 위주

| 대상 | 지표 | 방법 |
|---|---|---|
| 검색 | **재현율** | 사람이 만든 정답 집합과 비교. 영어 경로는 PatentAgentBench 무효 근거 셋(CN/US 80건)으로 잰다. KR은 무효심판 심결문의 인용문헌을 정답 일부로 쓰되 *유일한 정답으로 취급하지 않는다*. |
| 스크리닝 | **거짓음성률**(유효특허 전체 중 놓친 비율), 노이즈 누락률(노이즈 더미 중 유효 비율), 정밀도 | 전문가 라벨 50–100건 + **노이즈 무작위 표본 재검토** → 노이즈 누락률 r, 추정 거짓음성률 = r·N노이즈 / (N유효 + r·N노이즈) |
| 근거 | 인용이 실제로 주장을 뒷받침하는 비율, 링크 유효성 | 자동 검사(인용문이 원문에 있는지) + 표본 수동 검토 |
| 특허맵 | 집계 일치 | 스크립트 결과와 보고서 수치를 자동 대조 |
| 운영 | API 호출 수, 토큰 비용, 소요 시간 | 실행 로그 |

## 10. 결정할 것

1. **이름**: PARK는 가칭. KIPRIS는 기관 서비스 이름이라 저장소 이름에는 쓰지 않는 게 안전하다.
2. **라이선스는 영역별로 나눈다** → **결정:** 코드와 스킬은 Apache-2.0, 합성 데이터는 CC-BY-4.0, 모델은 별도로 정한다. claude-for-legal을 가져와 고치면 Apache-2.0 고지, ARIS 참고 부분은 MIT 고지가 필요하다.
3. ~~검토 백엔드~~ → **결정:** Claude 서브에이전트가 기본, Codex CLI는 선택(§4).
4. **문서 언어**: 스킬과 출력은 한국어 우선, README는 한/영 병기 제안.
5. **해외 특허**: MVP는 KR만(보고서에 범위 명시), 2단계에서 Google Patents 추가.
6. **KIPRIS 약관**: 데이터 재배포 범위, 대량 수집 허용 범위 확인.

## 12. 실제 CPU 작업에서 배운 것 (2026-11-09, 실제 과제 수행 기록 검토)

실제 캠퍼스 특허 유니버시아드 과제 수행 기록을 검토해 보니(과제와 팀은 밝히지 않는다), 지금 설계와 다른 점이 있다. 우선순위를 다음과 같이 조정한다.

| 실제로 한 일 | PARK 현재 | 조정 |

## 11. 변경 내역

- **v0.9 (2026-11-09)**: 청구항 대비표 (신규성·진보성).
  - `park chart`: 대상 청구항을 구성요소로 나눈다. 한국어 청구항의 ';' 나열 구조를 쓰고, 끝의 대상 이름을 E0으로 둔다. 기준일(우선권일) 이전 문헌 중 유사도 상위와 심사관 인용 KR 문헌을 고른다.
  - 심사관 인용은 공개번호로 오므로, 검색 API로 출원번호를 찾는다. 이때 출원번호 필드는 대조에서 뺀다. 다른 문헌의 출원번호와 같은 숫자인 공개번호가 실제로 있었다.
  - `park merge-chart`: 문헌 × 구성요소 판정의 인용문을 지정 청구항 또는 요약 원문과 대조한다. 보고서에 "청구항 대비" 절(● 개시 · ◐ 일부 · ○ 미개시 표, 문헌별 요약, 결합 논리)을 추가했다.
  - 실제 사례 하나에 적용한 결과:
    - 판정 40건의 인용이 모두 원문과 일치했다.
    - 모든 구성요소를 개시한 단일 문헌은 없었다.
    - 가장 가까운 문헌은 심사관 인용이 아니라 PARK 검색 7위 문헌이었다.
    - 반대로 심사관 인용 문헌의 유사도 순위는 18위와 1,465위였다. **글자 유사도 검색만으로는 심사관 검색을 대신할 수 없다.** 그래서 심사관 인용과 사용자가 아는 문헌을 항상 함께 넣는다.
  - 한계: 요약과 청구항만 대조하고 명세서 본문·도면은 보지 않는다. 보고서에 이를 명시한다.
  - 침해·회피설계 모드는 제품 설명이 필요해서 자동화하지 않았다.

- **v0.8 (2026-11-09)**: 2단계 — 핵심특허와 SWOT.
  - KIPRIS 서지 상세 API(호출 1회에 청구항 전문, 인용문헌, 법적상태)와 피인용 API를 확인해 클라이언트에 넣었다 (`docs/kipris-api-notes.md`).
  - `park shortlist`: 호출 예산 안에서 2단계 대상을 고른다. 초점 출원인 전부 + 기술분류별 상위 + 점수순.
  - `park enrich`: 청구항을 `fulltext/`에 저장해 근거 등급 'confirmed'를 쓸 수 있게 했다. 삭제된 청구항과 종속항을 걸러 독립항을 고른다.
  - `park review-batches` / `merge-review`: 독립항과 신호(피인용 백분위 등)로 핵심·주목·일반을 판정하고, 인용이 **지정한 번호의 청구항** 원문에 있는지 대조한다.
  - `park swot`: 기술분류별 성장(최근 구간 대 이전 구간), 출원인별 분포·등록 비율·핵심특허·평균 피인용을 집계하고, 규칙 기반 S·W·O·T 후보를 낸다. SWOT 해석도 `{{swot...}}` 자리표시자로만 숫자를 쓴다.
  - 보고서에 핵심특허 표와 SWOT 절(출원인 × 기술분류 매트릭스)을 추가했다.
  - 실제 주제 적용 결과:
    - 압축 목록 300건의 청구항 인용 300건이 모두 지정 청구항 원문과 일치했다.
    - 등급별 평균 피인용은 핵심 16.1, 주목 5.8, 일반 1.4건으로 등급과 일관됐다.
  - 직접 검토로 고친 것:
    - 강점 후보 규칙에 '분류 1위 출원인' 또는 '핵심특허 보유'를 추가했다. 비중 규칙만으로는 1위 출원인의 강점 분야를 놓쳤다.
    - SWOT 문장 중 데이터로 뒷받침되지 않는 시장 관련 서술을 지웠다.

- **v0.7 (2026-11-09)**: 판정 학습 정렬과 추정 재현율.
  - 정렬 실험(`docs/experiments/2026-11-09_ranking.md`)에서 판정으로 학습한 글자 n-그램 정렬이 다국어 임베딩 모델보다 나았다. CPU로 수 초에 끝난다.
  - 그래서 `park rank --learn`과 `park batches --next N`을 추가했다.
  - 실제 주제에 적용한 결과:
    - 학습 정렬로 고른 미선별 상위 구간의 유효 비율이 64%였다. 직전 라운드보다 크게 높다.
    - 새 꼬리 표본에서는 유효가 4%로 떨어졌다.
  - 보고서에 **추정 재현율**(찾은 유효 ÷ (찾은 유효 + 꼬리 추정))과 95% 범위를 표시한다. 이번 실행은 약 87%(73–94%)였다.
  - 보고서의 직접 쓴 숫자 검사(`--strict`)는 분석 해석을 쓰는 쪽(사람이든 LLM이든)에게도 그대로 적용된다. 실제로 선별 방법 설명에 쓴 구간 크기 숫자가 걸렸다.

    - 순위 상위 2,000건까지 선별을 넓혔다 (`--prefix r2`).
    - 새 꼬리 표본에서는 유효가 15%로 줄었다.
  - 꼬리 표본에 라운드 개념을 넣었다. 추정에는 가장 최근 라운드만 쓴다. 병합 시에는 나중에 쓴 결과 파일이 이기고, 꼬리 표본 표시는 다시 판정해도 유지된다.

  - Codex 선택 백엔드(`scripts/codex-screen.sh`)를 추가했다. 사용량 한도로 멈추면 다시 실행해 이어 간다.

  - 추가한 장치: 숫자 자리표시자(`{{stats}}`)와 직접 쓴 숫자 검사, 인용문 원문 대조, 노이즈 재검토 표본(`audit-sample`), `--count-only`, 자동 병합 출원인 목록(`applicant_merges.csv`)과 `match=exact` 별칭.
  - Codex 코드 검토(`docs/reviews/2026-11-09_codex_phase0-code.md`) 12건을 모두 반영했다. 주요 항목:
    - 자체 CSV를 다시 반입할 때 열이 충돌하던 문제를 고쳤다.
    - 권리 상태는 '상태 + 조회일' 묶음으로 다뤄, 가장 최근 관측값이 남게 했다.
    - 공백·너무 짧은 인용과 위치가 안 맞는 인용을 차단했다.
    - 재집계 때 이전 차트를 삭제하도록 했다.
    - 캐시된 응답은 처음 받은 날짜를 유지하고, 호출 예산은 실제 네트워크 호출만 센다.
    - 선별 파일이 비어 있으면 0건으로 집계한다.
    - 한글에 붙여 쓴 숫자("총999건")도 잡아낸다.
    - '노이즈 누락률'과 '추정 거짓음성률'을 구분했다.
    - 외국 법인 표기는 이름 끝에 따로 떨어진 단어일 때만 제거한다 ('에이지테크' 오병합 방지).
  - 지난 학기 데이터 9,976건으로 확인한 사실: 법인 표기를 떼면 다른 회사가 같은 이름이 되는 경우가 실제로 있다 ("(주)디티에스" ↔ 미국 "디티에스, 인코포레이티드"). 그래서 자동 병합 목록을 사람이 검토하는 단계를 넣었다.
